## Notes

**Salt convention (decided here, was unspecified):** `user_hash = sha256(USER_HASH_SALT + ':' + phone_or_group_id)`, lowercase hex, 64 chars — matching `VARCHAR(64)`. One application-wide salt in `USER_HASH_SALT`, **not** per-row: `user_hash` has to be a stable lookup key reproducible from the raw chat ID across messages, which per-row salting makes impossible. Consequence, stated plainly: this resists casual disclosure and cross-database correlation, but a leaked salt plus a phone-number list makes the hashes reversible by brute force — the number space is small. Rotating the salt invalidates every existing `user_hash` and cascades away the linked `message_logs`, so rotation is a data migration, not a config change. Implemented in `backend/app/core/hashing.py`.

**Migration tooling:** no Alembic. The schema is hand-written DDL owned by [[01_PostgreSQL_Schema]], and autogenerated diffs from an ORM this project does not have would only fight it. `backend/app/db/migrate.py` applies `app/db/migrations/*.sql` in filename order, recording each in `schema_migrations`. Each file is also *internally* idempotent (`IF NOT EXISTS`, `DO $$ … EXCEPTION WHEN duplicate_object`), so replaying the raw DDL on a database that already has the schema is a no-op too — test-verified, both paths.

**`updated_at` behaviour worth knowing:** the documented trigger uses `CURRENT_TIMESTAMP`, which is *transaction* start time. An insert and update inside one transaction produce an identical timestamp; the trigger only shows a change across separate transactions. Real usage (worker updating `fact_items` in its own transaction) is unaffected — the test asserts across transactions for this reason.

Run: `python -m app.db.migrate`.

`fraud_blacklists` (financial fraud) stayed out of scope for Sprint 1 — the table is deliberately absent from `001_init_schema.sql`, and a test asserts it does not exist so a stray future migration doesn't quietly reintroduce it. The open salt question from this card's original notes is now closed by the convention above; the anonymization claim in [[02_Value_Proposition]] has a documented mechanism behind it.

Still open, carried from [[01_Documentation_Audit_Report]]: `message_logs.extracted_text` stores plaintext user content with no retention/deletion policy. Anonymized identity does not make message bodies anonymous — decide retention before [[Create Audit Logging]] starts writing rows.
